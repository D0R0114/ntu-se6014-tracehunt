## Correctness fixes completed before merge

- Invalid and failed tool calls are recorded in the evidence ledger.
- Evidence ledger records stable SHA-256 query hashes.
- Successful search calls record the exact read request and returned document IDs.
- `run_sequence_query` now enforces chronological ordering instead of only checking that an entity appears in every step.
- Sequence matches return the document IDs and timestamps used to prove the ordered chain.
- Sequence scans report `complete: false` when the scan cap or missing required fields make absence-of-match unsafe to interpret.
- `date_histogram` uses the field requested by the caller.
- `TRACEHUNT_MAX_DOC_IDS` controls evidence fetch limits.
- Aggregation truncation is surfaced instead of silently hiding extra buckets.
- Field-name validation rejects wildcard/raw-DSL-style input.
- M3-style ECS field paths such as `event.code`, `host.name`, `user.name`, `source.ip`, `destination.ip`, and `process.command_line` are covered by regression tests.

## Evidence ledger contract

The ledger is append-only JSONL. It is the audit trail for hunt execution.

For successful calls, the record contains the run ID, tool, exact read request, SHA-256 query hash, result count, returned document IDs, timestamp, and duration.

For rejected or failed calls, the record contains `status: "error"`, the attempted typed input, the error, and the stable query hash.

M5 should cite ledger entries when producing hunt verdicts. M6 should keep a stable `TRACEHUNT_RUN_ID` per frozen run and compare query hashes/evidence across repeated runs.

## Validation and guardrails

- index allowlist
- bounded time window
- bounded result size
- bounded sequence scan
- bounded evidence document IDs
- bounded aggregation buckets
- typed filters only: `eq`, `match`, `exists`
- validated field names
- no write path in the MCP backend
- Elasticsearch read-only role in `m4-mcp/es/readonly_role.json`
